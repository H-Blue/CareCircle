# Presentation transport

In **Menu → Your account → your circle → Transport after recording**, the leader can enable or disable presentation transport. Status shows member consent, carrier approval, delayed triggers, message drafts and delivery receipts. Only the circle leader can change the mode. This is a presentation feature using the existing cloud scheduling appointments, not a hospital/Epic connection.

Tapping Finish on a normal completed recording requests an authenticated Oracle event. Its due time is 20 seconds after the server receives that request. The original request is retried when visit metadata uploads; the recording ID keeps retries from resetting the timer. Offline delays start the timer after reconnection. Interrupted recordings do not request texts. The worker waits for a matching completed cloud recording before proceeding. It reads the current cloud schedule after the timer, drafts a brief request with Oracle AI, validates the patient/date/time, and uses a factual template if drafting is unavailable. It does not send transcripts or clinical details to contacts.

The current test schedule is November 3, 2026 at 5 PM, November 13 at 2 PM, and December 2 at 8 AM, America/Chicago. Requests are marked DEMO. Each current consenting circle member can receive one request per uncovered appointment. Duplicate recordings do not resend an already submitted request for that appointment/member. A later recording may retry a request that expired without submission or was definitely rejected. Uncertain submissions are never retried automatically. The presentation window expires after ten minutes, preventing old blocked demos from suddenly sending days later.

Twilio sends **SMS**, which appears in Apple Messages; this integration does not send blue-bubble iMessages. The configured toll-free sender must be approved. On a trial account, recipient numbers must also be verified with Twilio. Every recipient must sign in and save their own SMS consent. Membership alone and sign-in verification do not grant transport-message consent. Leaving, turning the feature off, withdrawing consent or replying STOP prevents future sends. START clears a provider opt-out, but the person must save consent again; it does not enroll them automatically.

A shared 20-message UTC-day budget covers the original coordinator and this feature. Claimed messages, including uncertain attempts, consume a slot. Acceptance by Twilio is distinct from delivery; signed callbacks update the app status. YES/NO replies must include the per-request code. The first current member to explicitly accept is assigned; the leader receives a confirmation notice, subject to their own consent and the daily budget. This confirms the outbound ride only, not a return ride. Demo confirmation replies must arrive within the presentation window.

Queue state lives privately in the existing versioned Oracle coordinator bucket; account membership and consent remain in Oracle NoSQL. The worker runs in the Oracle service and recovers scheduled jobs after restart. The bounded prototype retains up to 200 recording triggers and 1,000 message records and requires developer cleanup at that limit. Nothing is placed in public image/recording links. Requests/callbacks are authenticated, and message bodies and phone numbers are excluded from server request logs.

Verification: `python -m unittest discover -s Server` checks timing with a controlled clock, duplicate/restart safety, authenticated circle isolation, consent, STOP, provider blocking, daily limits, YES replies and callbacks. `Server/Cloud/check_transport.py` uses temporary synthetic accounts **without consent** to check the live timer and drafting without sending any SMS. The simulator account fixture likewise never sends provider messages.
